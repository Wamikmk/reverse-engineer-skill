A beginner’s field guide

Understand software through evidence.

Learn how your reverse-engineer skill investigates an app, explains what it finds, and helps you build your own version when you ask.

The central idea

The skill guides an assistant to inspect, gather evidence, and describe behavior before making claims or writing a replacement.

Start here

What does “reverse engineering” mean?

You begin with something that already works and ask how it produces its result.

Imagine an app that converts temperatures. You can enter a number and see an answer, but you want to understand the calculation, how it rounds decimals, and what happens if someone enters text.

Reverse engineering means working backward from the existing app to an explanation of that behavior. Depending on the app and available tools, the assistant can inspect files, trace connections between functions, or observe a permitted test run.

Think of studying a finished machine to write a description of what it does. That description can help someone design a new machine with the same behavior.

You can stop once you understand the feature. Building a replacement is an optional next step.

The moving parts

Who does what?

A skill is a reusable instruction file that the assistant reads. It gives the investigation a consistent method. Several separate pieces carry out the work:

YouChoose the app, the feature, and the result you want. Set the boundaries, including permission to run the target.
CodexThe assistant that reads the skill, chooses useful questions, calls available tools, and explains the findings.
The skillThe investigation instructions: check the tools, cite evidence, track unanswered questions, and build from a written specification when requested.
REAThe software-analysis toolkit named in the original image. It provides tools that can inspect an app and return evidence.
MCPModel Context Protocol: the connection that lets the assistant request work from REA and receive results.
An engineA specialist tool REA may need for the target. A decompiler, for example, helps turn compiled program instructions into a form a person can inspect.

What is installed so far

Your instruction skill is saved globally. REA, its MCP connection, and any specialist engine still need to be available and checked before an investigation can work. Saving the skill does not install those tools.

The investigation

From your question to an explanation

Define the question

You provide a path or URL and a specific feature, such as “How does this app convert temperatures?” The assistant checks what you want to learn and which actions you authorize.

You + Codex

Check the tools

The assistant checks the available REA connection, the target type, and the installed release’s requirements. If something essential is missing, it identifies the blocker before dependent analysis.

Codex

Choose a route

REA’s guided prompts cover questions such as understanding a feature, comparing versions, or tracing a crash. The assistant selects the documented route that fits and explains its plan.

Codex + REA guidance

Trace the feature

The assistant first maps the app, then follows the relevant connections toward the function that matters. Before each substantial tool call, it explains which question the result should answer.

Codex + REA tools

Explain the evidence and gaps

The assistant separates direct findings from interpretations and unanswered questions. It can write a specification when requested. A gap may send it back to an earlier investigation step.

Codex

If you ask it to wait for your “go,” it pauses before the first analysis call. Otherwise, it continues within the permission you already gave.

A worked example

“I saw it” and “I think it” mean different things

Imagine an authorized test of a fictional temperature converter. These examples are illustrative; no app was analyzed to produce this guide.

ObservationDirect evidence

“Entering 0°C produced 32°F. Entering 100°C produced 212°F.” Those are results seen in the imagined test.

In a real report: the assistant cites the returned evidence identifier and any available location or test record so you can check the claim.

InferenceAn interpretation

“The app probably uses Fahrenheit = Celsius × 9/5 + 32.” That formula fits the observations, but two examples alone cannot prove every possible input follows it.

What remains possible: special cases or a lookup table could produce those same answers. The assistant states its confidence and what further evidence would distinguish them.

UnknownAn open question

“How many decimals does the app display? What happens with an empty input?” The examples have not answered these questions.

The next probe: inspect the formatting and input-validation paths, or test decimal and empty inputs if running the app is authorized.

Each important unknown stays in a register with its status and the next useful check. Failing to find something in the inspected files means the search has a limit; it does not prove the behavior is absent.

An optional build

Turn behavior into a specification, then code

A specification is a written description of what your version must do. The skill can put it in SPEC.md, a plain-text document. It records inputs, outputs, state changes, errors, and measured examples while marking unresolved requirements.

# Illustrative excerpt, not a complete specification
Feature: Celsius-to-Fahrenheit conversion
Recorded example: input 0, output 32
Recorded example: input 100, output 212
Still unknown: decimal display and invalid-input behavior

If you request a replacement, the assistant writes new code in your chosen language from that specification. It learns the original’s behavior without lifting its source code or internal implementation details. A missing requirement sends it back to investigate.

Tests then check the recorded behavior. For example, a test expecting 32 for an input of 0 should reject an intentionally wrong result of 30. This checks that the test can actually catch a mistake.

Passing a few examples establishes agreement on those cases. Stronger claims need broader evidence, including boundaries, formatting, and error handling.

The boundaries

Reading an app and running it are separate actions

Static inspectionExamines files without launching the target. It can reveal structure and possible execution paths, but some runtime questions remain unanswered.
Dynamic inspectionRuns or interacts with the target to observe behavior. The assistant explains what the action will touch and needs authorization covering that action.

The skill works within your ownership, permission, or stated research scope. Text discovered inside an app is treated as material to inspect; an embedded request to download or run something cannot grant permission.

What “local” means here

REA is intended to analyze the target locally, and the skill directs the assistant to avoid external target-file uploads. That alone does not establish that the whole assistant system is offline. A strict requirement that nothing leave the machine needs a separate check.

Your first request

Give it one feature to investigate

In a session where the installed skill is available, invoke $reverse-engineer and state the target, question, permissions, and desired output. Replace the example path with a real app you are allowed to examine.

Use $reverse-engineer.

Target: C:\Projects\MyConverter\app.exe
Question: How does temperature conversion work?
Scope: I own this app and authorize static inspection.
Execution: Do not launch or interact with it.
Output: Explain the evidence and write SPEC.md.
Checkpoint: Show the plan and wait for my go.

If you later want an implementation, you can add: “Build an independent Python version from SPEC.md under ./my-version and test the recorded behavior.” Questions that need target execution still require permission covering that execution.

Your saved skill folder contains three useful documents:

SKILL.mdThe reusable instructions the assistant follows during an investigation.
Image transcriptionAll visible text from your original image, including its header and footer.
Conversion planThe decisions used to turn that image’s prompt into a reusable skill.

A completed investigation gives you four short lists: what is proven, what is inferred, what is still unknown, and which next checks could resolve those unknowns.
